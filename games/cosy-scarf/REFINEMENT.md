# Cosy Scarf: thirty refinement passes

Progress: pass 20 done and published (`iter-20.png` taken). Next: pass 21.

Each pass follows the [refinement loop](../../docs/solutions/workflow-issues/refinement-loop-for-kid-3d-readability.md): screenshot or record, write an honest critique, make one focused set of changes, re-screenshot, and re-measure. Passes that fix a place where the game contradicted one of the jam's compound docs say which doc.

**How each pass was measured.** Look passes use a fresh-state production build (`npm run build`, served by `vite preview`), 1180×820, touch, on a fake clock (Playwright `page.clock`, 33 ms steps), with the shot taken 6.5 s after load so the idle glow and the first ghost-hand demonstration are in frame. Motion passes record the same build as frame sequences. Every pass then re-runs the shared jam probe (`perf-probe.mjs`, with `--browser chromium`, since it defaults to WebKit) on the production build: Chromium, 6× CPU throttle (CDP), 1180×820, DPR 2, touch, 4 s warm-up, 10 s of sampling with 12 scattered taps (30 s from pass 3 on: at 2.6 fps, 10 s is only 26 frames, too few for a steady p95). From pass 5 on the probe runs twice per pass, because one 30 s run at 6× swings by about 1.5 ms either way; the table gives the worse run, with the other as the repeat. From pass 17 on, a pass that touches the late game also probes a seeded save (all four animals warm, every scarf worn), where the draw calls double. The probe reports `cpuP95Ms` (the game's own update plus render submit per frame, from `window.__jamPerf`) and the renderer's draw calls. The cloud VM has no GPU (Chromium renders with SwiftShader at about 2.6 fps at DPR 2), so frame rate here says nothing about an iPad; CPU per frame and draw calls are the proxies, and WebKit fps is compared against Pebble Table in the same session at the end. No physical iPad was measured.
