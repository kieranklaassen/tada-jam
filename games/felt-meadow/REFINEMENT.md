# Felt Meadow: thirty refinement passes

**Progress:** all thirty passes done and published; the owner's checklist is met, the media (hero, four iteration stills, a 49 s walkthrough) are in the Project store, and the PR body is handed off. Nothing is pending.

The brief asked for thirty passes that make a needle-felted nature table read clearly to a four-year-old and stay cheap on an old iPad. Each pass: screenshot → honest critique → one focused set of fixes → re-screenshot → perf re-measure.

**How each pass was measured.** A fixed meadow is seeded into storage: a red flower in plot 1, a blue flower in plot 2, plot 3 bare, a loose purple seed on the grass, and red pollen already on the bee. The still is the production build at 1180×820, DPR 2, with the tier pinned to 0 (every effect on), taken after 6.4 s of game time so the idle glow and the ghost-hand demonstration are in frame. Game time runs on Playwright's paused fake clock (`page.clock.install()` then `pauseAt`, advanced in 100 ms steps) because this VM renders with SwiftShader and cannot hit real time. The draw calls and triangles in the table come from that still. The CPU numbers are the shared perf probe (`perf-probe.mjs`: Chromium, 1180×820 DPR 2 touch, 3 s warm-up then 5 s of samples) at 6× CPU throttle, once with `?tier=0` pinned (every effect, so CPU regressions show) and once on the automatic tier. The probe reports `cpuP95Ms`, the 95th-percentile JavaScript time per frame from `window.__jamPerf`. Frame rate on this VM is GPU-bound in software rendering and says little about an iPad; the CPU column is the budget the passes defend (under 8 ms at 6×).

Screenshots are in the Project store under `media/jam-10-games/felt-meadow/` (`iter-01.png`, `iter-10.png`, `iter-20.png`, `iter-30.png`, `hero.png`, `walkthrough.mp4`).

## Still weak

What thirty-one passes did not fix, plainly:

- **No physical iPad was measured.** Every number here comes from Chromium and WebKit with software rendering on a 4-core cloud VM. The CPU budget holds with room to spare, but frame rate on a real tablet GPU, the iOS audio unlock on the lift of a touch, and the first-touch cost are unverified on hardware.
- **The top tier is heavy in software rendering.** Pinned to tier 0, WebKit on this VM runs the meadow at 7 fps, below Pebble Table's 13 on its own automatic quality; the automatic tier leaves tier 0 within seconds and then runs 22 to 23 fps. Tier 0's costs (DPR 2, the blur, a multisampled post target, three fuzz shells) are fill, which a tile GPU handles far better, but that is unmeasured.
- **Edges below the top tier.** Tier 1 keeps the post pass without multisampling, so its horizon still steps a little (pass 30).
- **Tier 2 buys little over tier 1** in software rendering (pass 16); on a tile GPU it should buy more, but that is a guess until it runs on one.
- **The first touch costs about 175 ms at 20× throttle** (about 17 ms unthrottled): creating the audio context must happen inside the gesture (pass 19).
- **The mouse hides a little under half the time.** That is its nature, but a child who looks for it in the first minute can miss it (passes 12 and 27).
- **An interrupted demonstration replays from the start** rather than resuming, which reads fine but is one more hand than strictly needed.
- **The audit reads shapes, not pixels.** Pass 31's audit checks the meshes on the CPU, so a crossing drawn by a shader it cannot see would pass; the meadow's felt has no such shader today.
- **About 21 KB of garbage per drawn frame** remains (pass 26), mostly three.js's render-list sort and numbers boxed between calls; a major collection runs about every 10 s in a 4 to 8 ms task.
